# Сервер картинок 2.0

Сервис для загрузки изображений и получения прямых ссылок на них. Метаданные изображений хранятся в PostgreSQL, список изображений показывается постранично, базу можно резервировать и восстанавливать. Техническое задание — [project_description.md](project_description.md) и дополнение [project_description_2.md](project_description_2.md), план первой версии — [project_plan.md](project_plan.md).

> В ТЗ для обработки HTTP-запросов в качестве примера указана стандартная библиотека (`http.server`). Backend реализован на FastAPI: он даёт асинхронную обработку параллельных запросов, встроенный разбор multipart-форм и автоматическую документацию API (`/docs`).

## Стек и архитектура

- Python 3.12+, FastAPI и Uvicorn — HTTP API и HTML-страницы.
- PostgreSQL 16 и psycopg2 — таблица `images` с метаданными загруженных файлов.
- Pillow — проверка фактического формата изображения.
- Nginx — прямая раздача загруженных файлов из общего тома `images` и статики из `static/`; остальные запросы проксируются в FastAPI.
- Docker Compose — сервисы `db`, `app` и `nginx`, именованные volumes `images` и `db_data`, папка `logs/` подключена с хоста.
- Интерфейс сверстан на чистых HTML и CSS, без JavaScript: страницы в `templates/`, стили и картинки в `static/`.

## Адреса и маршруты

| Метод и маршрут | Обработчик | Назначение |
|---|---|---|
| `GET /` | FastAPI | Главная страница: приветствие, описание сервиса, ссылки на загрузку и список. |
| `GET /upload` | FastAPI | Страница загрузки: форма выбора файла, поле со ссылкой на последнюю загрузку. |
| `POST /upload` | FastAPI | Загрузка изображения и запись метаданных в базу (описание ниже). |
| `GET /images-list?page=N` | FastAPI | Список изображений из базы: таблица, по 10 записей на странице, кнопки удаления. |
| `GET /images/<имя_файла>` | Nginx | Прямая ссылка на изображение для просмотра и скачивания. |
| `GET /images/` | Nginx / FastAPI | Старый адрес каталога, перенаправляет (301) на `/images-list`. |
| `POST /delete/<id>` | FastAPI | Удаление изображения: запись из базы и файл с диска. |
| `GET /static/...` | Nginx | CSS и картинки интерфейса. |
| `GET /health` | FastAPI | Проверка состояния backend: `{"status": "ok"}`. |
| `GET /docs` | FastAPI | Автоматическая документация API (Swagger UI). |

Пользовательский адрес — `http://localhost:8080` (Nginx), backend напрямую — `http://localhost:8000`. Ссылки на изображения всегда ведут на Nginx; адрес задаётся переменной окружения `PUBLIC_BASE_URL` в `compose.yaml`.

### `POST /upload`

Принимает multipart-поле `file`. Поддерживаются JPG, PNG и GIF до 5 МБ (5 МиБ) включительно; Pillow проверяет, что содержимое действительно является изображением и соответствует расширению. Файл сохраняется в `/images` под уникальным именем `<uuid>.<расширение>`, а в таблицу `images` добавляется запись: сгенерированное имя, оригинальное имя, размер в байтах, формат и время загрузки.

Запись в базу и сохранение файла выполняются в одной транзакции:

- если база недоступна или `INSERT` не прошёл — файл на диск не пишется;
- если файл не удалось записать — транзакция откатывается;
- если не прошёл `COMMIT` — уже записанный файл удаляется.

В любом из этих случаев изображение не сохраняется, а причина пишется в `app.log`.

Форма на странице `/upload` отправляет файл этим запросом, и браузер получает ту же страницу со ссылкой на изображение или с сообщением об ошибке. Остальным клиентам, например `curl`, сервер отвечает JSON:

```bash
curl -F "file=@photo.png" http://localhost:8080/upload
```

```json
{"id": "6deacbfdd83f461fb00d8a84b45fc4d0", "db_id": 1, "url": "/images/6deacbfdd83f461fb00d8a84b45fc4d0.png", "full_url": "http://localhost:8080/images/6deacbfdd83f461fb00d8a84b45fc4d0.png"}
```

`id` — UUID в имени файла, `db_id` — идентификатор записи в таблице `images` (он используется для удаления). Ошибки: 400 — файл не прошёл проверку (`{"detail": "Поддерживаются только форматы JPG, PNG и GIF"}`), 503 — база данных недоступна. Браузер отличается по заголовку `Accept: text/html`.

### `GET /images-list`

Таблица изображений из базы, сначала последние загруженные (`ORDER BY upload_time DESC`): имя файла со ссылкой `/images/<имя_файла>`, оригинальное имя, размер в КБ, дата и время загрузки, тип файла и кнопка «Удалить».

Пагинация — по 10 записей, номер страницы в параметре `page` (`/images-list?page=2`). Выборка делается запросом:

```sql
SELECT id, filename, original_name, size, upload_time, file_type FROM images
ORDER BY upload_time DESC, id DESC LIMIT 10 OFFSET <(page - 1) * 10>;
```

Кнопки «Предыдущая страница» и «Следующая страница» неактивны на первой и последней странице. Некорректный номер (`abc`, `0`, `-5`) открывает первую страницу, номер за концом списка перенаправляет на последнюю. Если записей нет, показывается «Нет загруженных изображений»; если база недоступна — сообщение об ошибке и HTTP 503.

### `POST /delete/<id>`

Отправляется кнопкой «Удалить» в списке. Удаляет запись `DELETE FROM images WHERE id = <id>` и файл из `/images` в одной транзакции, затем перенаправляет (303) обратно на ту же страницу `/images-list`. Ошибки:

- 404 «Изображение не найдено» — записи с таким `id` нет (браузеру показывается список с сообщением, остальным — JSON);
- 422 — `id` не число;
- 503 — база данных недоступна.

Если запись есть, а файла на диске уже нет, запись всё равно удаляется, а в лог пишется ошибка. Имя файла из базы перед удалением сверяется с шаблоном `<32 hex-символа>.jpg|png|gif`, поэтому удалить что-то за пределами `/images` нельзя. Удаление, как и ссылки на изображения, не требует авторизации — её нет в ТЗ.

## База данных

Сервис `db` в `compose.yaml` — образ `postgres:16-alpine`, контейнер `postgres_container`, база `images_db`, пользователь `postgres`, пароль `password`, данные в volume `db_data`, порт 5432 открыт на хосте для отладки. Таблицу создаёт [init.sql](init.sql) при первом запуске контейнера с пустым volume; backend при старте дополнительно выполняет `CREATE TABLE IF NOT EXISTS` и пишет в лог, удалось ли подключиться.

```sql
CREATE TABLE images (
    id SERIAL PRIMARY KEY,                              -- уникальный идентификатор записи
    filename TEXT NOT NULL,                             -- имя файла, сгенерированное сервером
    original_name TEXT NOT NULL,                        -- имя файла от пользователя
    size INTEGER NOT NULL,                              -- размер файла в байтах
    upload_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,    -- время загрузки
    file_type TEXT NOT NULL                             -- формат файла: jpg, png, gif
);
```

Работа с базой вынесена в [db.py](db.py) (`ImageRepository`): пул соединений psycopg2, все запросы параметризованы. Подключение настраивается переменными окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DB_HOST` | `localhost` (в Compose — `db`) | хост PostgreSQL |
| `DB_PORT` | `5432` | порт |
| `DB_NAME` | `images_db` | имя базы |
| `DB_USER` | `postgres` | пользователь |
| `DB_PASSWORD` | `password` | пароль |
| `TZ` | `Europe/Moscow` | часовой пояс для `app.log` и `upload_time`; задаётся переменной `TZ` на хосте или в файле `.env` |

Посмотреть записи:

```bash
docker exec -it postgres_container psql -U postgres images_db -c "SELECT * FROM images ORDER BY upload_time DESC;"
```

## Резервное копирование

Резервные копии создаются утилитой `pg_dump` внутри контейнера `postgres_container` и сохраняются в папку `backups/` с датой и временем в имени: `backups/backup_2025-01-24_153000.sql`.

### Создать копию

Контейнеры должны быть запущены (`docker compose up`). Из корня проекта:

```bash
python backup.py
```

Скрипт выполняет `docker exec postgres_container pg_dump -U postgres --clean --if-exists images_db`, проверяет код возврата (при ошибке недописанный файл удаляется) и пишет результат в `logs/app.log`. Дополнительные зависимости не нужны — только Python 3.10+ и Docker.

Оставить только N последних копий:

```bash
python backup.py --keep 7
```

Та же копия вручную, без скрипта:

```bash
docker exec -t postgres_container pg_dump -U postgres images_db > backups/backup_2025-01-24_153000.sql
```

### Восстановить базу

```bash
python backup.py --restore backups/backup_2025-01-24_153000.sql
```

или вручную:

```bash
docker exec -i postgres_container psql -U postgres images_db < backups/backup_2025-01-24_153000.sql
```

Копии, сделанные скриптом, содержат `DROP TABLE IF EXISTS`, поэтому восстанавливаются поверх существующей таблицы: её содержимое заменяется данными из копии. Файлы изображений хранятся в volume `images` и в копию базы не входят.

### По расписанию

Windows (Планировщик заданий), ежедневно в 03:00:

```powershell
schtasks /Create /SC DAILY /ST 03:00 /TN "image_storage backup" /TR "python F:\path\to\image_storage\backup.py --keep 7"
```

Linux/macOS (`crontab -e`):

```text
0 3 * * * cd /path/to/image_storage && python3 backup.py --keep 7
```

## Логирование

Действия пишутся в `logs/app.log` в формате `[Дата/время] Действие: сообщение`:

```text
[2026-10-16 19:55:21] Успех: подключение к базе данных установлено.
[2026-10-16 19:55:24] Успех: изображение e02c7a4bea2e445f9fe8a1c004e9a6f1.jpg (id=14, t0.jpg, 0.6 КБ) загружено.
[2026-10-16 19:55:25] Ошибка: метаданные не сохранены, изображение t0.jpg не загружено (server closed the connection unexpectedly ...).
[2026-10-16 19:52:14] Просмотр: открыт список изображений (страница 2 из 2).
[2026-10-16 19:52:14] Успех: изображение d50ee5364287499985bf99353e8b9d85.jpg (id=1) удалено.
[2026-10-16 19:52:25] Ошибка: изображение с id=99999 для удаления не найдено.
[2026-10-16 19:55:25] Успех: создана резервная копия backup_2026-10-16_195525.sql (3.6 КБ).
[2026-10-16 19:52:39] Успех: база данных восстановлена из backup_2026-10-16_195238.sql.
```

Логируются просмотры страниц, загрузки (успешные и отклонённые с причиной), ошибки базы данных, удаления (включая «файл отсутствует на диске» и «id не найден»), резервное копирование и восстановление, а также запросы к несуществующим маршрутам и неподдерживаемым методам. Папка `logs/` подключена в контейнер `app` с хоста, поэтому backend и `backup.py` пишут в один файл. Отдачу самих изображений выполняет Nginx, она попадает в его access-лог (`docker compose logs nginx`).

Случайное UUID-имя затрудняет угадывание ссылки, но не является авторизацией: любой, у кого есть ссылка, может открыть изображение.

## Запуск в Docker

Установите Docker Desktop и выполните из корня проекта:

```bash
docker compose up --build
```

Откройте `http://localhost:8080/`. Backend стартует после того, как PostgreSQL пройдёт проверку `pg_isready`. Для остановки нажмите Ctrl+C или выполните `docker compose down`; данные в volumes `images` и `db_data` сохраняются между перезапусками (`docker compose down -v` удалит их).

- Nginx и пользовательские маршруты: `http://localhost:8080`
- backend: `http://localhost:8000`
- PostgreSQL: `localhost:5432`
- лог приложения: `logs/app.log` в папке проекта

На Linux контейнер `app` работает от непривилегированного пользователя; если он не может писать в `logs/`, выполните `chmod 777 logs`.

## Запуск локально

Требуются Python 3.12+ и запущенный PostgreSQL (например, только сервис базы: `docker compose up -d db`).

```bash
python -m venv .venv
```

Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Установка зависимостей и запуск:

```bash
python -m pip install -r requirements.txt
uvicorn app:app --reload --host 127.0.0.1 --port 8000
```

Локально файлы и логи сохраняются в `images/` и `logs/` рядом с приложением, база ищется на `localhost:5432` (см. переменные `DB_*`).

## Тесты

Тесты не требуют Docker и PostgreSQL: вместо `ImageRepository` в `create_app()` передаётся таблица в памяти с тем же интерфейсом, файлы и логи пишутся во временные каталоги.

```bash
python -m unittest
```

```text
├── app.py              # FastAPI-приложение: маршруты, проверка, сохранение, список, удаление, логирование

├── backup.py           # резервное копирование и восстановление базы через pg_dump/psql
├── requirements.txt    # зависимости Python
├── Dockerfile          # multi-stage образ backend на Python 3.12
├── compose.yaml        # сервисы db, app и nginx, порты, volumes
├── nginx.conf          # раздача /images/ и /static/, проксирование остального в backend
├── templates/          # HTML-страницы: index.html, upload.html, images_list.html
├── static/
│   ├── css/            # reset.css и style.css
│   └── img/            # иконки и картинки главной страницы
├── tests/              # автоматические тесты backend
├── images/             # локальный каталог изображений (в Docker — volume images)
├── logs/               # app.log (в Docker подключается в контейнер app)
└── backups/            # резервные копии базы backup_<дата>_<время>.sql
```
